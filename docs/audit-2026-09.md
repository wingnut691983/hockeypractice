# Part 1: New findings

## Critical

### 1.1 Manager and site-admin codes are hashed with unsalted single-round SHA-256
`HockeyPractice/Util/Security.cs:12-17`

```csharp
var bytes = SHA256.HashData(Encoding.UTF8.GetBytes(input.Trim().ToUpperInvariant()));
```

No salt, one round. Two things make this matter more here than it would elsewhere:

1. **The database is designed to leave the building.** `SiteAdminController.DownloadBackup`
   hands one out, and `VolumeBackupService` uploads the whole volume to R2 nightly. CLAUDE.md
   already states "an archive can forge access, not just leak data". That is the threat model
   this hash has to survive, and it does not.
2. **`ToUpperInvariant()` case-folds the site admin code.** `SiteAdminController.cs:80-81`
   passes `SITE_ADMIN_CODE` straight into `HashCode`. The uppercasing is correct for team
   codes (alphabet is uppercase by construction, `Security.cs:10`) but it silently destroys
   case in an operator-chosen passphrase. A 14-character mixed-case code loses roughly 14 bits
   before it is ever hashed.

Keyspaces against a leaked archive, at a conservative 10 GH/s on one consumer GPU:
player code 31^6 (about 9e8, seconds), manager code 31^8 (about 8.5e11, minutes to an hour),
site admin code whatever was typed, case-folded, unsalted. One rainbow table covers every team
at once because there is no per-row salt.

**Fix:** PBKDF2 or Argon2 with a per-row salt for `ManagerCodeHash` and the admin code. These
are verified about once per 180 days, so any work factor is affordable. Keep `ViewCode` in
plaintext (`Team.cs:44-52` justifies that correctly: it is a shared secret the coach re-shares).
Stop uppercasing the admin code specifically, or document that it is case-insensitive.

**Note:** changing the hash invalidates existing manager codes, so this needs a rotation path
or a dual-read window.

## High

### 1.2 Anyone can lock the site admin out of their own site
`HockeyPractice/Program.cs:130-133`

```csharp
var slug = http.Request.RouteValues["slug"] as string;
var key = string.IsNullOrWhiteSpace(slug) ? "site-admin" : "team:" + slug.ToLowerInvariant();
```

Every slug-less request shares one bucket at 30/minute with `QueueLimit = 0`. An unauthenticated
attacker posting to `/admin/login` 30 times a minute keeps the real admin at a permanent 429,
including when they need to lift a stuck `MaintenanceState` pause or run a restore.

`known-issues.md` #8 covers the *team* budget being shared. It does not cover this: the comment
at `Program.cs:128-129` reasons only about guessing rate ("at 14 characters it is not the thing
anyone is guessing"), never about denial.

**Fix:** partition the admin login on something the attacker does not control and the admin
does, or give a successful-auth path an exemption, or accept a much lower limit with a longer
window plus a bypass. Given the address is not trustworthy (`Program.cs:220-221` clears the
proxy lists deliberately), a cookie-seeded partition with a low limit is probably the shape.

### 1.3 Nothing enforces the admin code length the comment relies on
`HockeyPractice/Controllers/SiteAdminController.cs:80-81`

```csharp
var code = config["SITE_ADMIN_CODE"];
_adminCodeHash = string.IsNullOrWhiteSpace(code) ? null : Security.HashCode(code);
```

No minimum length, no charset requirement. The rate limiter's safety argument at
`Program.cs:128-129` is a hope about an environment variable. Combined with 1.1 and 1.2 this
is the weakest link in the admin surface.

**Fix:** refuse to configure below N characters and surface it through `StartupHealth` the way
migration failures already are (`Program.cs:166-167`), rather than failing silently open.

### 1.4 Static assets are served with no `Cache-Control`
`HockeyPractice/Program.cs:258`

```csharp
app.UseStaticFiles(new StaticFileOptions { ContentTypeProvider = contentTypes });
```

No `OnPrepareResponse`. The middleware emits `ETag` and `Last-Modified`, so every asset is
**revalidated with a conditional GET on every navigation**: one full round trip each, on rink
wifi, for the 67 KB stylesheet, the 155 KB wordmark, the icons, and every pdf.js file.

The stylesheet and favicons already carry `?v=` hashes (`_Layout.cshtml:19,27,28`), so
`max-age=31536000, immutable` is safe for them today with no further work.

This is separate from `known-issues.md` #9 (no compression). Compression fixes bytes; this
fixes round trips, and on high-latency wifi the round trips are the larger cost.

**Fix:** `OnPrepareResponse` setting a long immutable max-age for versioned paths and a short
one for the rest. Add `asp-append-version` to the two logo images (see 1.6) so they qualify too.

### 1.5 Uploaded images cost about four database queries each, every page view
`HockeyPractice/Controllers/DrillController.cs:454-473`, `HockeyPractice/Controllers/TeamController.cs:248-265`

Both end in `PhysicalFile(path, contentType)`, which gives `ETag` and 304 handling (correctly
noted at `DrillController.cs:470-471`) but no `max-age`. So every diagram on every plan view is
a conditional GET, and each of those revalidations runs the full pipeline: `ResolveAsync` at
`:456` (a `Teams` query, possibly a `Players` query, and `OtherTeamsAsync`), then the
`DrillDiagrams` query at `:461-463`, then a `File.Exists`.

A 12-drill plan with a diagram each is roughly 48 database queries plus 12 stat calls on a
repeat view that should have been 12 cache hits.

Diagram filenames are fresh GUIDs on every save (`PlanStorageService.cs:239`), so they are
immutable by construction and `max-age=31536000, immutable` is exactly correct.

**Fix:** set the header on both actions. Optionally short-circuit the `If-None-Match` check
before `ResolveAsync`, though that trades a little authorization strictness for speed and is
probably not worth it once the max-age lands.

### 1.6 The wordmark is 155 KB and loads on every page
`HockeyPractice/wwwroot/logo-wordmark.png` (155,373 bytes, 880x275 RGBA PNG),

### 1.8 `LoggingEmailSender` logs full message bodies including tokens

### 1.9 Team logo upload trusts the browser's Content-Type and stores bytes unmodified
`HockeyPractice/Controllers/CoachController.cs:1124-1143`

```csharp
var contentType = logo.ContentType?.ToLowerInvariant() ?? string.Empty;
if (!AllowedLogoTypes.Contains(contentType)) return "Logo must be a JPEG, PNG, GIF or WebP image.";
var ext = contentType switch { "image/png" => ".png", ... _ => ".jpg" };
...
await source.CopyToAsync(destination);
```

No magic-byte check, no decode, no dimension check, no re-encode. This is the direct opposite of
both sibling upload paths: the PDF path sniffs `%PDF-` (`PlanStorageService.cs:64`) and the
diagram path decodes and re-encodes to WebP (`:274-316`). `PlanStorageService.cs:216-218` even
names the logo path as the exception.

Two consequences:

- **Security (moderate):** arbitrary bytes land on the persistent volume under an `image/*`
  name that `TeamController.Logo:256-264` then serves. Because the extension is derived from the
  allowlisted type there is no route to `.html` or `.svg`, and `nosniff` (`Program.cs:243`)
  blocks sniffing, so this is not XSS. It is unvalidated arbitrary-content storage.
- **Performance (larger):** a coach can upload a 2 MB PNG that is then served **on every page of
  that team**, uncached (1.4), undimensioned, and unconverted.

There is also no `[RequestSizeLimit]` on the branding action (`:1030-1033`), so the 2 MB check
at `:1122` only fires after Kestrel has buffered up to its 30 MB default.

**Fix:** route the logo through the existing `ShrinkToWebpAsync` in `PlanStorageService.cs:274`.
It already does the sniff, the pixel cap and the re-encode.

### 1.10 A crafted image produces an unhandled 500 and loses the coach's work
`HockeyPractice/Services/PlanStorageService.cs:311-312`

```csharp
catch (Exception ex) when (ex is UnknownImageFormatException or InvalidImageContentException
                              or NotSupportedException)
```

`Image.LoadAsync`, `Mutate` and `SaveAsWebpAsync` can also throw `ImageProcessingException`,
`InvalidOperationException` and `OutOfMemoryException`. None is caught here; the caller at `:262`
catches only `IOException`, and `DrillController.AddDiagramsAsync:826` catches nothing.

A structurally-valid image that fails mid-decode is a 500, and the coach loses everything typed
into the drill form. The careful partial-success messaging at `AddDiagramsAsync:841-847` never
runs.

The OOM case is real rather than theoretical: the header-only pixel cap is 50 M pixels
(`ShrinkToWebpAsync:285-293`), which is about 200 MB of RGBA during resize in a memory-limited
container.

**Fix:** widen the filter to catch `Exception` and return `NotAnImage`, the way the PDF path
already handles a malformed document. Consider lowering `MaxDiagramPixels`.

### 1.11 `RotateCode`'s documented purpose is not what it does
`HockeyPractice/Controllers/CoachController.cs:1096-1108`, `HockeyPractice/Program.cs:47`

The docstring says rotating the code is "how a coach cuts off someone who has left the team". It
is not. Access lives entirely in a signed cookie claim with a 180-day sliding expiry and no
server-side session store, so rotation stops *new* joins and evicts nobody. Every device already
holding a claim keeps full access for up to another 180 days, sliding on each visit.

The only actual revocation is replacing the Data Protection key ring, which signs everyone out
of everything.

This is severity-high not because the design is wrong (the 180-day cookie is a defensible product
call, argued at `Program.cs:46`) but because a coach will read that docstring, rotate the code
after a safeguarding incident, and believe the person is out.

**Fix:** correct the docstring at minimum. If real revocation is wanted, a per-team epoch integer
stamped into the claim and compared on each request is the cheap version.

### 1.12 Drill tags on the plan editor appear or vanish depending on which library page you are on
`HockeyPractice/Controllers/CoachController.cs:1192-1196`, `HockeyPractice/Views/Shared/_DrillRow.cshtml:44`

`PlanDrillsAsync` loads:

```csharp
.Include(pd => pd.Drill).ThenInclude(d => d!.Diagrams)
```

with no `.Include(d => d.Tags)`. `_DrillRow.cshtml:44` reads `Model.Drill.Tags.Count`, and lazy
loading is not enabled (no `UseLazyLoadingProxies` in `Program.cs`). So the tag pills on a plan's
own drill rows are populated only by EF relationship fix-up, which happens only when that same
drill also appears on the currently-displayed page of the library picker below (that query does
`Include(d => d.Tags)` at `CoachController.cs:1219`).

Net effect: the same drill in the same plan shows tags on library page 1 and shows none on page 2.

`PlanController.cs:44-46` omits `Tags` deliberately for the player view, and that view does not
use `_DrillRow`, so it is correct. The editor is the one that got it wrong.

**Fix:** add `.ThenInclude(d => d!.Tags)` to `PlanDrillsAsync`.

# Batches

Each batch below is one deployable unit: a coherent change, verifiable on its own, safe to ship
without waiting for any batch it is not explicitly blocked by. Every deploy goes to production
(`hockeypractice`, ebhockeyplan.com), so "shippable alone" is the property that matters.

Three rules shaped the grouping:

1. **Things that change every response on the site travel together.** You want one deploy where
   every page's headers changed, not three.
2. **Things that can lock a user out travel alone.** If a manager cannot sign in, the cause must
   be unambiguous.
3. **Things that touch the same method travel together**, so the method is read, changed and
   tested once.

## At a glance

**A wave is priority order, not a shipping unit.** It says what to do next and what blocks what.
What ships together is the "Ships as" column, and nothing else. Wave 0 happens to be a single
deploy; Wave 2 is seven separate ones.

"Ships as" has three values:

- **Alone.** Must not be bundled with anything. Either it changes every response on the site or it
  can lock someone out, so a regression needs exactly one candidate cause.
- **D<n>.** Its deploy unit. Batches sharing a number go out together.
- **Fold in.** No deploy of its own; goes with whatever batch already has the file open.

### Batch C: Admin code floor and limiter partition  ✅ SHIPPED in v29
**Contains:** 1.3 (enforce a minimum `SITE_ADMIN_CODE`), 1.2 (stop the anonymous admin lockout),
and the **case-folding** half of 1.1's write-up. **Not the hashing.**
**What this did and did not touch, because the first version of this note overstated it.** The
admin code's hash turned out never to be persisted: `SiteAdminController` derives it from the
environment variable at startup and compares against a hash of what was just typed. So dropping
its case-folding needed no migration, and it went in here. That is all that changed.
**The KDF is untouched.** `HashCode` and `HashSecret` are both still unsalted single-round
SHA-256; the only difference between them is the `ToUpperInvariant`. `CoachCodeHash` and
`ViewCodeHash` still go through `HashCode` and are still stored, so the substance of 1.1, that a
downloaded or leaked archive yields every manager code in under an hour, is **fully open**. Do not
read this batch as having reduced that.
What it did establish is that batch D is **manager codes only**: the admin code has no stored hash
for an attacker to crack, so it needs no KDF work and no migration window.
**Reproduced before and after:** under the old shared bucket an attacker sending 35 attempts left
the real admin, with the correct code, on a 429. After: the attacker exhausts only their own
bucket at 10 and the admin signs in. Team code entry unchanged at 30/min per team.
**Why together:** 1.2's whole safety argument is "the code is long enough that guessing is not the
threat". That is currently a hope about an environment variable. Fixing the limiter without fixing
the floor moves the weakness rather than closing it, and fixing the floor without the limiter
leaves the denial path open. Ship them as one statement about the admin surface.
**Change:** refuse to configure below a minimum length and surface it through `StartupHealth` the
way migration failures already are, rather than failing silently open. Repartition the limiter so
one anonymous caller cannot spend the admin's whole budget.
**Keep out:** 1.1. The hashing change has a migration problem and would hold this up for days.
**Risk note:** if the current production `SITE_ADMIN_CODE` is below whatever floor you pick, this
deploy locks you out of `/admin`. Check the configured value against the floor **before** pushing,
not after.
**Docs:** README Configuration table, and a "What I'd flag" entry for the limiter, since the
partition choice is genuinely non-obvious (the address is untrustworthy on purpose).

**After shipping:**
- Sign in at `/admin` with the real code. This is the check that the new length floor did not lock
  you out, and it is the first thing to do, not the last.

### Batch D: Manager code hashing  ✅ COMPLETE

**Contains:** the hashing half of 1.1. `Team.CoachCodeHash` only.

**Status: complete.** Steps 1 to 4 shipped 22 September 2026 as `v30` (commit `003af2a`), and
the manager codes were reissued on 23 September, which is the step that actually closed it.

**Why no waiting period was needed, despite the archives.** Nightly archives taken before the
rotation still hold the old single-round unsalted SHA-256 hashes, and retention keeps three. That
sounds like a three-night tail and is not one: those hashes are of codes that were rotated away.
Recovering one now yields a code that grants nothing. The exposure closed at rotation, not at
retention.

**What was NOT independently verified.** The production hashes live in a database this session
cannot read, and manager codes are hash-only by design, so "every team was rotated" rests on the
operator having done each one. A team missed during the rotation keeps its old-format hash
silently and indefinitely: the in-place upgrade in `TryGrantAsync` only fires when a code is
typed, and the access cookie means that may never happen. If there is ever doubt, the cheap check
is that a rotated hash starts `pbkdf2$` while an un-rotated one is 64 hex characters.

Verified locally against a planted old-format row: an existing code signs in (0.23s including the
rehash), the row becomes `pbkdf2$600000$...`, the same code then verifies against the new format,
a rotated code signs in, a new team is created in the new format, and four malformed stored values
are refused without an exception reaching the log.

**This was re-planned after two things were checked rather than assumed.** The first version
recommended rehash-on-next-signin with a dual-read window longer than archive retention. That
approach does not terminate here, and the scope was wider than it needed to be.

#### Why it is `CoachCodeHash` and nothing else

- **`ViewCodeHash` is not worth upgrading.** `Team.ViewCode` stores the player code in
  **plaintext** in the same row, deliberately, so a coach can re-share the join link all season
  (`Models/Team.cs`). A hash whose plaintext sits in the next column protects nothing. The one
  exception is a team created before `ViewCode` existed, where the hash is the only copy; that is
  a low-privilege code handed to every family on the team by design, so it is accepted rather
  than fixed. **Do not "make it consistent" by upgrading it.** Note the reason instead.
- **The site admin code has no stored hash at all.** It is derived from the environment variable
  at startup (batch C). Nothing in a database or an archive to crack.

So the entire exposure in 1.1 is one column, and the people affected are the one or two managers
per team, not the whole roster.

#### Why rehash-on-next-signin cannot be the mechanism

`TeamController.TryGrantAsync` is the **only** place `CoachCodeHash` is read. It runs when someone
types the code, then writes a claim into the auth cookie; every later request authorizes from that
claim and never touches the database hash again. The cookie lasts 180 days **and slides**, so a
coach who opens the site most weeks never re-enters their code at all.

A rehash that only fires on verification therefore has no end condition. The old hashes would sit
in the database indefinitely, which is exactly the thing the batch exists to remove.

#### The plan

1. **New format, written through `Security`.** PBKDF2-SHA256 with a per-row random salt, stored in
   one self-describing string in the existing column (`pbkdf2$<iterations>$<salt>$<hash>`).
   `CoachCodeHash` has no `MaxLength`, so it is an unbounded SQLite `TEXT` column and **this needs
   no migration**. Use `Rfc2898DeriveBytes.Pbkdf2` from the BCL: no new package, and nothing with
   native per-RID assets, which the csproj notes require of every dependency here.
   A manager code is verified about once per 180 days, so the iteration count can be high enough
   to be uncomfortable for an attacker and unnoticeable here.
2. **Verify accepts both formats**, told apart by shape: 64 hex characters is the old one, a
   `pbkdf2$` prefix the new one.
3. **Rehash on a successful old-format verify.** Not as the migration mechanism, which is the
   mistake above, but so that a hash arriving from a restored archive heals itself the first time
   it is used.
4. **Ship it.** One deploy, no breakage: every existing code still works through the old path.
5. **Then rotate every team's manager code** on the admin page and hand each coach the new one.
   That is what actually replaces the stored hashes, and it completes the moment it is done
   rather than waiting on anyone's behaviour.

#### What this removes from the old plan

- **No dual-read window measured in nights.** The window is now "until you finish step 5", which
  is minutes.
- **No removal step, and no three-night retention wait.** Step 2's old-format path **stays
  permanently**, on purpose: after step 5 nothing in the live database uses it, and the only thing
  that can bring an old-format hash back is a restore from an old archive, which is precisely when
  you want managers still able to sign in. Keeping it is what makes a restore safe, so do not
  tidy it away later.
- **Not "alone" any more.** It carries no migration and cannot lock anyone out, so it does not
  need a deploy to itself. It is still simplest to ship on its own.

#### The cost, stated plainly

Every manager enters a new code once. Players are untouched: player access never goes through this
column. With the current number of teams that is a handful of messages.

**Decision still needed:** none on approach. Just when you want to do step 5, since it needs you to
get the new codes to the coaches.

**Docs:** README "What I'd flag" (why only one of the three codes needed this, so nobody
"completes" the job later by upgrading `ViewCodeHash`), and the Roles section.

**After shipping step 4, before step 5:**
- Sign in as a manager with an existing code. This is the old-format path and must still work.
- Confirm the row rehashed: `CoachCodeHash` for that team now starts `pbkdf2$`.
- Sign in again with the same code, now against the new format.

**After step 5:**
